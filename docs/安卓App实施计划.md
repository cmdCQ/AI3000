# 易三千安卓 App 实施计划

> 状态：评估后的计划，尚未开始开发。
> 目标路线：使用 Capacitor 将现有 React/Vite 前端封装为 Android 混合 App；不重写 React 页面，不另做一套原生业务逻辑。
> 依据：当前仓库实际源码与现有接口结构；本计划不代表已创建 Android 工程、安装依赖或完成商店合规审核。

## 1. 已确认的产品目标

1. Android App 与现有网站共用账号、命盘、卦例、咨询和积分服务。
2. 用户可以在网页、App 之间切换；切换页面时尽量保留当前页面、命盘和咨询状态，避免重复排盘或重复加载。
3. 首期必须联网；不承诺离线 AI 或离线排盘。
4. 不改变现有会员等级、积分、游客规则、记录删除规则和后端算法。
5. 先做内部 APK / 真机验收，再决定是否提交应用商店。

## 2. 当前项目事实与影响

### 2.1 前端形态

- `/var/www/sqw.somtfly.com/src/app/package.json` 是 React 19 + Vite 8 项目，产物是多入口页面，不是单一 SPA。
- `/var/www/sqw.somtfly.com/src/app/vite.config.mjs` 会扫描各页面的 `index.html`；现有地址包括首页、`/my/`、`/my-charts/`、`/bazi-consult/`、梅花、六爻、登录和后台等。
- 现有页面大量使用同源绝对路径 `/api/...`、Cookie 登录和页面间普通链接。最小封装不需要迁移这些 URL，但 Android 返回键、外链和重新加载必须专门验收。

### 2.2 命盘与排盘

- `/var/www/sqw.somtfly.com/src/app/shared/chartsStore.js` 通过 `/api/charts` 和 `/api/charts/:id` 读取/保存命盘。
- `/var/www/sqw.somtfly.com/src/app/my-charts/main.jsx` 详情页由服务端 `/api/bazi/paipan` 根据原始出生参数重新排盘，前端不自行计算。
- 这意味着“缓存排盘记录”不能把缓存当成新的算法或权威数据源。建议缓存**已成功排盘的展示快照和请求指纹**，命盘原始数据仍以服务端授权结果为准。
- 若请求指纹相同且快照未过期，可先展示缓存，随后静默校验；若生日、时间、性别、地点或真太阳时相关字段变化，必须废弃旧快照，不能复用。

### 2.3 咨询与记录

- `/var/www/sqw.somtfly.com/src/app/bazi-consult/api.js` 使用同源 Cookie/Authorization，并通过 SSE 事件流接收 `delta` 和 `done`。
- `/var/www/sqw.somtfly.com/src/app/bazi-consult/main.jsx` 当前由 URL 参数定位命盘/咨询，支持恢复已保存消息、继续提问、停止生成及失败状态提示。
- 咨询必须区分：服务端已保存的完整记录、客户端临时草稿、正在生成的临时答案。App 切后台或进程被系统杀死时，不能把未完成内容冒充为已保存。

## 3. 推荐架构

### 3.1 第一阶段：Capacitor WebView 壳

- Android 只负责启动 WebView、状态栏/安全区、系统返回键、网络状态和应用生命周期。
- React 页面仍由现有 Vite 产物提供；后端仍是当前域名和接口。
- 优先采用远程加载现有站点或将同一份 Vite 产物同步到 App 资源，二者择一需在技术验证后决定：
  - **远程加载**：网站发布后 App 自动获得前端更新，最小改造；完全依赖网络。
  - **随包静态资源**：版本可控、启动更稳定；每次网页改动都要重新发 APK，且需要处理 API origin。
- 建议首个内部版本采用随包静态资源 + 固定 HTTPS API origin，避免把生产页面变成不可控的远程 WebView；网站仍保留正常访问。

### 3.2 页面状态与“无缝切换”

建立一个小型、可版本化的 `app bridge/cache` 层，不在每个页面各写一套缓存：

- **内存层**：记录当前页面、返回栈、当前 chartId/consultationId、正在生成状态。
- **持久层**：Preferences 只用于非敏感设置和缓存版本；IndexedDB 配合成熟的 TanStack Query 持久化适配器作为候选，先验证容量、恢复和账号隔离。命盘、出生资料、咨询和草稿均按个人信息处理，并非“无敏感性”。首版默认只做会话内存缓存；持久私有缓存需用户明确启用，并选择经维护的 Keystore 支持加密方案、验证锁屏/备份策略后再开启。不能用普通 Preferences 明文保存咨询全文。复用库的具体版本、许可证与 React 19 兼容性在 P0 核对，不自研另一套请求状态管理库。
- **服务端层**：登录后的命盘、咨询、卦例和积分数据仍以服务端为准。

缓存键建议：

- `bazi:chart:{chartId}:{fingerprint}:v1`：排盘响应中的展示事实、服务端版本/时间、请求指纹、缓存时间。
- `bazi:consultation:{consultationId}:v1`：最近一次已确认的消息列表和更新时间；不保存 token、密码或完整身份凭证到自定义缓存。
- `page:last-route:v1`：最近页面和必要的 query 参数。
- `draft:consultation:{requestId}:v1`：未发送文字或未完成回复草稿，带过期时间和状态标记。

缓存规则：

1. 展示缓存只用于快速首屏，不得绕过登录、命盘归属检查或积分检查。
2. 进入命盘详情时先显示同指纹缓存；联网成功后用服务端新结果替换，失败则明确标注“缓存内容/暂未更新”，不静默当成最新结果。
3. 排盘快照只缓存成功响应；400/401/403/404/503、部分响应和未知结构不得写入。
4. 咨询消息只有服务端 `done.status=completed` 且 `save.status=saved` 才进入已保存缓存；partial/stopped/failed 只恢复为草稿。
5. 请求发出前保存 requestId；网络失败后不得自动生成新 ID 重发。现有咨询服务端有 requestId 防重逻辑，但当前页面 `run()` 每次生成新 ID，且现有哈希包含目标参数；首轮取得 consultationId 后用不同目标重放可能冲突。P2 必须核对并保留首次 payload/目标和 ID，先恢复服务端已保存状态；不能把前端自动重试当作现成能力。停止/中断费用沿用当前服务端实际用量规则，不承诺零扣费。
6. 用户退出账号、切换账号或命盘授权失败时，清理对应私有缓存；不得让下一个账号看到上一个账号的命盘。
7. 缓存设置 TTL 和总容量上限，超限按最近最少使用清理；用户主动删除记录时同步删除本地对应缓存。
8. 初始参数建议（待真机压测）：列表 staleTime 30 秒、已加载分页最多 5 页；排盘事实快照最长 24 小时、最多 30 盘；仅内存咨询最近 10 个，草稿最多 24 小时；总持久数据上限 20 MB。这些是提议，不是现有功能。
9. 指纹包含实际请求字段、chartId/修订标识、缓存 schema 和服务端算法版本。当前接口无可靠算法版本时，需增加响应版本或随发布主动失效。大运/流年等当前日期相关展示带业务日期，跨日重新校验；不把含 prompt 的响应无差别持久化。
10. 网页与 App 通过服务端同步，不共享本地缓存；回前台、网络恢复及进入详情时重新校验。当前无推送变更接口，另一设备删除后不能保证立即清除离线副本；私有离线阅读不列入首期。

### 3.3 页面切换策略

- **仅复用一个 WebView 不等于无缝切页。** 当前普通链接跳转会销毁页面 JS/React 状态，单例内存缓存也会丢失；Capacitor 本身不会替本项目解决这个问题。
- 为达到本次目标，新增可选的 App 单入口壳，优先复用 React Router 管理首页、命盘列表/详情、卦例列表/结果、咨询和我的；把这些页面的组件与 `createRoot` 启动入口分离，保留网页现有 URL 与多入口兼容，不全站重写。
- 当前命盘详情存在直接写 DOM、全局事件及模块启动副作用，必须在迁入 App 路由前改为可挂载/卸载的组件或隔离适配器，清理监听与未完成请求；不是给链接加拦截就能直接复用。后台管理不纳入 App 首期路由。
- 页面路由留在同一个 React 根节点；TanStack Query 候选用于请求去重、内存缓存和失效，路由状态用于列表筛选、滚动锚点和草稿。无需所有页面永久 keep-alive，以免多个咨询运行时和事件监听常驻。
- 普通页面切换使用 App 内导航，不打开外部浏览器，不让每个页面都重新创建 WebView；外部 HTTPS 链接交系统浏览器，不向任意远程页面暴露原生 bridge。
- 系统返回键优先关闭弹窗/键盘，其次返回页面栈，最后退出 App；不能直接把所有返回都解释成退出。
- 命盘详情离开再返回：恢复缓存骨架并校验，不重新计算算法；服务端失败时保留清晰的过期提示和重试按钮。
- 咨询页离开再回：恢复 `consultationId`、消息和草稿；正在生成的请求通过 AbortController/生命周期处理，回到页面后不能显示假完成。
- 梅花、六爻结果页和记录页同样保存当前 recordId/筛选条件，但不把一个术数的缓存误用到另一个术数。

## 4. 登录与接口适配

当前后端 CORS 固定网站域名，而 App 的 origin 不是网站域名。开发阶段应二选一并验证：

1. WebView 仍使用网站 HTTPS origin：改动少，但需要接受远程页面依赖。
2. App 静态资源使用独立 Capacitor origin：为 App origin 增加受控 CORS/预检、Cookie 或 Token 策略，并覆盖 GET/POST/PATCH/DELETE/OPTIONS；不能简单放开 `*`。

推荐优先验证第二种，但若 Cookie 在 WebView 与 API 域名之间不稳定，应统一改为安全的 Authorization token 存储方案，并评估迁移风险；不得把 token 明文写入普通缓存或日志。

需要专项验证：注册/发短信、登录、退出、账号注销、过期登录、重新登录、命盘归属、积分 401/403/429、咨询 SSE、删除记录和后台权限。后端不新增“App 专用旁路”，沿用现有权限和计费入口。

## 5. 分阶段实施

### P0：技术验证（1～2 人日）

- 建最小 Capacitor Android 工程，不改业务页面。
- 验证 React 19/Vite 8 产物能装入 WebView，HTTPS API、登录 Cookie/Authorization 和 SSE 能工作。
- 验证系统返回键、键盘、安全区、切后台/恢复、断网/恢复。
- 结论门：若静态资源 origin 导致认证或 SSE 不稳定，采用网站 HTTPS 远程加载或明确的 API origin 方案，不在 P1 继续堆补丁。

### P1：App 单入口导航与缓存基础（6～10 人日）

- 增加统一 bridge/cache 模块和版本化键，不修改服务端排盘算法。
- 为 `/my-charts/` 列表、命盘详情和记录页接入“缓存首屏 + 网络校验”。
- 做账号隔离、TTL、容量、删除同步和缓存失效。
- 接入 App 返回栈和生命周期，不改变网页端的正常行为。

### P2：咨询与流式生命周期（3～5 人日）

- 缓存完整咨询消息和未完成草稿，恢复 consultationId。
- 覆盖 SSE 断流、手动停止、切后台、重复点击、重试幂等和积分提示。
- 验证普通网页端不产生重复发送、重复扣费或旧账号数据泄漏。

### P3：真机和发布准备（3～6 人日）

- Android 版本兼容、横竖屏、不同输入法、弱网、系统回收、深色/浅色策略（若不支持深色则明确保持现有主题）。
- 图标、启动页、签名、版本号、崩溃采集策略和隐私权限清单。
- 生成内部 APK/AAB，完成人工验收；再单独评估应用商店备案、AI/传统文化内容审核和隐私材料。

### 总体估算

- 最小可安装内部 APK：约 1～2 人日。
- 带单入口无缝导航、会话缓存、返回恢复和真机回归的内部版本：约 13～23 人日。
- 加入用户可选加密持久缓存、完整发布收尾的首版：约 18～30 人日，不含审核等待；各阶段有交叉，非固定报价。
- 相比最初 7～12 人日封装估算，上调原因是本次明确要求无缝切页：现有多入口/DOM 副作用需要适配单入口，且私有缓存需要账号隔离、失效和隐私设计，并非只安装 Capacitor。
- 原生重写不在本计划内，预计至少 30～60 人日以上。

## 6. 验收标准

### 功能

- 网页/App 共用一个账号，切换后不串命盘、卦例、咨询和积分；当前网页 Cookie 不能直接假定可在 App 静态 origin 共享，P0 必须先验证 origin 与认证策略。
- 命盘详情缓存可快速显示，但服务端校验结果最终覆盖；参数变化不会显示旧盘。若首期采用仅内存缓存，则 App 内页面切换可无缝恢复，进程被系统杀死后回到服务端加载；持久离线缓存必须通过额外隐私验收。
- 咨询离开再回能恢复已保存消息；未完成生成只恢复草稿或失败状态，不显示为已完成。
- 返回键符合页面栈预期；退出账号清理私有缓存。

### 安全与权限

- 未登录不能通过缓存读取私人命盘或咨询。
- 401/403/404/429/503 均有明确界面，不用缓存伪造成功。
- 删除服务端记录后本地缓存同步失效；不同账号不能读取同一设备上一个账号的缓存。
- 不在日志、截图、崩溃报告中记录手机号、Token、出生资料或咨询全文。

### 性能

- 首次进入命盘详情可先展示有效缓存骨架；缓存过期时明确更新状态。
- 同会话有效缓存下的列表/详情返回：目标首个有效内容 ≤200 ms（不含网络校验），保留筛选和滚动位置，不整页刷新。过期缓存可发一次去重的校验请求；无缓存仍需网络，不承诺固定耗时。导航绝不自动发送 AI 咨询。
- SSE 在真实 HTTPS、弱网、切后台、恢复后行为可解释，且不重复计费。

### 发布前测试

- Vite 构建使用显式临时 outDir；写接口和付费 AI 全部 mock。
- React/Vitest：缓存键、指纹、TTL、账号隔离、失效、状态机和幂等测试。
- Playwright：320/390/500/1280 宽度、返回栈、命盘缓存、咨询恢复和错误态。
- Android 真机：至少覆盖一台低/中端设备和一台较新设备，记录系统与 WebView 版本；在 P0 根据所选 Capacitor 当前支持矩阵确定最低 Android、JDK、Gradle 与 SDK 版本，不沿用过时模板。覆盖注册/登录、排盘、记录、咨询、积分、退出、切后台、断网恢复。
- 后端：只验证现有权限和接口契约；不得用真实付费 AI 或真实业务记录做测试。

## 7. 不在首期做的事情

- 不重写成 React Native/原生 UI。
- 不实现离线排盘或离线 AI。
- 不新增 App 专用计费、会员或权限规则。
- 不把客户端缓存当作服务端数据库，不在本地永久保存敏感身份资料。
- 不因做 App 顺手重构现有网页、多页面入口或后端算法；单入口适配只在 App 壳/共享组件边界内逐步迁移，网页入口和行为保持兼容。
- 不承诺应用商店审核一定通过；商店提交是后续独立决策。

## 8. 需要实施前确认的选项

1. 首版采用“随包静态资源”还是“远程加载网站”；本计划默认先验证随包静态资源。
2. 是否启用含个人信息的加密持久命盘缓存；默认仅会话内存缓存。启用前明确告知内容、期限、清理入口和设备备份行为。
3. App 是否需要推送通知、分享、相册/文件导出；默认不做。
4. 是否只发布内部 APK，还是准备应用商店材料；默认先内部验收。

## 9. 当前结论

本项目最合适的路线是 **Capacitor + 现有 React/Vite 页面 + 统一缓存/生命周期层**。真正的难点不是把网页装进 APK，而是认证 origin、系统生命周期、SSE 咨询恢复、缓存权限隔离和应用商店合规。后续获得开发授权后先执行 P0 技术验证；P0 未证明认证与流式稳定前，不进入大范围缓存开发。本次只交付计划，不启动 P0。
