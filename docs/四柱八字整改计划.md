# 易三千 · 四柱八字体验与 AI 分方面整改计划

> 状态：用户已批准实施；P0/P1/P2 正在进行，P3 等待用户提供 prompt。以下勘察与阶段方案保留为基线，实际验证结果见末尾实施记录。
> 代码基线：`1476dbe`；开始勘察时工作区干净。
> 用户目标：保留已经满意的梅花易数、六爻；解决选盘入口不合理、八字详情尤其 AI 卡片与另外两者割裂、五方面共用输出模板的问题。具体新 prompt 由用户后续提供，不在本计划中代写。

## 一、结论先行

1. **这不是迁移遗漏，而是迁移完成后保留下来的旧产品结构。** 前端已集中到 React/ESM 的 `src/app/`，但八字详情仍为 React 外壳 + 命令式渲染；换了技术外壳不代表体验已经统一。
2. **选盘页像登录页，是因为它确实使用登录页模板。** 文案说“选择命盘开始排盘”，实际点击进入已有命盘详情；游客、空态、新建入口的层次也没有按八字用户任务重新组织。
3. **八字 AI 已经复用同一个引擎，不需要再造第三套。** 割裂主要来自额外包装层、独立标题/折叠、硬编码旧金色和不同的卡片层级。
4. **方面参数没有丢。** 前端传 `tab`，后端识别方面，盘面上下文含专项分析，RAG 也随方面变化；真正没有分开的是首次解读的 system 和固定全量输出骨架。因此应修“输出契约与模板分流”，而不是只改按钮或多拼一句“重点分析事业”。
5. 推荐顺序：**补保护测试 → 整理选盘入口 → 统一八字详情与 AI 外观 → 收到用户 prompt 后完成服务端分方面 → 隔离验证与分批发布。** UI 与 prompt 可以分别推进，不必为了等 prompt 停住 UI，也不能把 UI 完成说成 AI 内容已完成。

## 三、问题与代码证据

> 下列路径均相对仓库根目录，行号对应本计划基线。

### 3.1 选择命盘：页面身份与用户任务错位

- `src/app/select-chart/main.jsx:114-147` 使用 `.auth-wrapper > .auth-card`；`src/app/select-chart/style.css:22-24` 导入登录页样式。
- `src/app/shared/css/auth.css:18-29` 是整屏居中、最大宽度 380px 的认证布局；梅花/六爻则使用术数页面外壳，而非认证外壳。
- `src/app/select-chart/main.jsx:117-118` 的标题/说明是品牌名与“选择命盘开始排盘”；`src/app/select-chart/selectChart.logic.js:95-97` 的卡片目标却固定是 `/my-charts/?id=...`。这实际是“选择已有盘查看”，不是选择模块后发起新的排盘流程。
- 空态自身有新建按钮，页尾仍永久渲染新建链接（`src/app/select-chart/main.jsx:68-77,141-143`）。应该重新确定主次和单一主要任务，而非简单删掉游客新建能力。
- `src/app/select-chart/main.jsx:26-49` 用可点击 div 做整张卡，无原生链接键盘行为；错误态无显式重试动作（同文件 `81-87`）。
- `type` 支持 charts/ziwei/meihua；新建链接带 `from`（`src/app/select-chart/selectChart.logic.js:8-35`），但 `src/app/charts/logic.js:46-58` 仅消费 action/id，并未承接 from。不能仅凭存在标签就宣称对应模块工作流已经实现。

**方向：保留 URL，重定义 charts 模式为清楚的八字入口。**

### 3.2 八字详情：不是缺少组件，而是两层外观叠加

- `src/app/my-charts/main.jsx:98-142`：写详情骨架 → 请求 `/api/bazi/paipan` → `BaziRender.render()` → `BaziAI.mount()`。React 只管理外壳，内部由命令式模块写 DOM。
- `src/app/lib/myChartsView.js:181-192`：四柱 → AI → 其他信息。这是既有明确交互约束，不能为了“统一”把 AI 移到整页末尾。
- 梅花/六爻通过 `src/app/shared/mhysAiPanel.js:12-25` 与 `src/app/shared/liuyaoAiPanel.js:11-24` 配置同一个 `aiPanel.js`。
- 八字同样接入该引擎，但 `src/app/shared/baziAiPanel.js:77-114,393-413` 又加了自己的标题、折叠、方面条和历史区，并通过 CSS 隐藏公共 header。
- `src/app/shared/baziAiPanel.js:81` 的选中态仍写死 `#b8960a`；当前设计令牌主色为 `#1f6b5e`（`src/app/shared/css/tokens.css:45-69`）。这不是主观猜测，浏览器计算样式实测仍为旧金色。

**方向：统一视觉语言与单一标题/折叠所有权；保留八字方面、历史等领域功能。** 五行颜色有业务语义，不应不分用途全部涂成品牌色。

### 3.3 五方面 prompt：已有专项输入，仍然全量输出

实际链路：

```text
/my-charts/?id=...
  → ChartsStore.get(id)
  → POST /api/bazi/paipan（原始出生参数）
  → BaziRender + BaziAI.mount
  → 用户选方面并主动点开始
  → aiPanel 引擎调用 BaziAI 配置的 buildBody
  → POST /api/bazi/parse {出生参数, tab, chartId, question, 可选 followUp/context}
  → 后端重新生成盘面、鉴权/额度/游客闸门
  → 首次：报告模板 + 盘面上下文 + 方面 RAG → 流式输出
  → 正常完成：记额度；登录用户首次解读存记录
  → GET /api/bazi-analyses?chartId=... → 按方面展示最新与旧版
```

证据：

- `src/app/shared/baziAiPanel.js:133-146` 明确发送 `tab: state.cur`。
- `src/server/auth-server.js:2117-2118` 校验五方面并回退综合。
- `src/server/paipan/bazi_prompt.js:308-316` 为专项加入对应 `life_aspects` 数据。
- `src/server/auth-server.js:2156-2174` 的所有首次解读都调用 `baziReportPrompt()` 与 `baziReportSystem()`。
- `src/server/paipan/bazi_report.js:288-291,315-320` 只有同一用户模板，要求按统一 system 输出“命盘评分 + 综合内容”，方面通过标题和“重点展开”指定。
- 追问已分支：`src/server/auth-server.js:2156-2185` 切追问模板/system，并且不存为新解读。

**准确诊断：不是五个最终请求逐字相同，而是专项输入未对应到独立输出规格。** 不应该重复发送整份八模块报告后再用前端隐藏无关部分。

### 3.4 保护不足与附带发现

- `src/app/tests/my-charts.spec.mjs` 主要保护列表、菜单与删除；`src/app/tests/my-charts-detail.logic.test.mjs` 仅有少量纯 HTML 约束，不能证明成功详情与 AI 链路正常。
- 选盘已有游客/空态/列表快照、状态/URL 测试，但缺键盘、焦点、模块承接及完整新建回跳保护。
- 详情排盘错误响应没有保留 status，可能显示“排盘失败（undefined）”（`src/app/my-charts/main.jsx:111-119`）。列为同页异常态修复，不与算法变更混在一起。
- 详情请求只传原始出生参数；真太阳时一行目前是显示信息（`src/app/lib/myChartsView.js:153-158`）。需另外确认用户预期与实际算法策略，不能在本轮悄悄修成不同的盘；也不能把“页面与 AI 一致”误当“真太阳时一定正确”。
- 部分说明仍保留迁移时期措辞；当前 README 的单测数量也落后于实测，提及的 `duipan/` 在当前工作树不存在。算法基线需先确认可取得的历史来源与运行条件，不能声称已经执行。仅在改动相关范围内更正，不扩成全文文档清理。

以下是额外的 **AI 链路风险，不是本次已修复的事项**，应在 P0 建复现判据，影响本轮操作安全的再单独拆项处理：

- `src/server/auth-server.js:3026-3067` 对部分失败/输出截断的成功判定较弱，非空正文可能仍被计费和保存；`src/app/shared/aiPanel.js:698-734` 的缓存也不能单凭非空即视为完整成功。需明确完成、取消、上游错误与长度截断的边界。
- `src/app/shared/aiPanel.js:453-538` 的追问使用独立局部 XHR，不在主流取消句柄中；八字切方面调用的主流 abort 不等于追问也已停止。统一 UI 时必须覆盖追问跨方面的迟到响应。
- 追问仅携带当前报告正文末尾 1200 字，不包含完整多轮历史；专项要点可能被截掉。若需变更上下文长度/策略，应评估成本并单独确认，不默认为已支持完整多轮。
- 服务端结束响应后才保存，前端延迟 200ms 重拉历史存在竞态；保存失败也缺少明确客户端完成通知。后续不要将延时当作可靠一致性保证。
- 解读记录关联 chartId 的所有权/出生参数匹配、并发额度预占、历史模板版本追溯等仍需独立设计。当前查询按用户隔离，不应把关联校验不足夸大成已经证实跨用户泄露。
- 八字流虽使用 `text/event-stream` 响应头，正文实际是裸文本增量和积分尾巴，不是标准 `data:` 帧。任何完成信号改造要考虑现有 XHR 兼容，不可直接替换协议影响另外两路。

## 四、建议的产品与组件方案

### 4.1 选盘入口

推荐保留 `/select-chart/?type=charts`，先不强制合并或重定向到“我的命盘”。两者共享卡片信息模型，但职责分开：这里是“选一份盘继续看”，我的命盘仍是管理入口。

- 标题明确“四柱八字”，说明明确“选择已有命盘查看，或新建一份”。
- 采用术数页面的页头、内容宽度、留白和返回方式，不再整屏登录模板。
- 列表态提供一个清楚的新建入口；空态把新建作为主操作，避免两处同权重重复按钮。
- 游客仍可登录、注册、新建，不先闪加载态，也不发私有列表请求。
- 保留 loading/guest/empty/error/list 五态；401 给重新登录引导，其他失败提供重试。
- 卡片用真实链接，支持 Tab、Enter、新标签打开；辅助按钮用 button，不用伪链接。
- 暂不新增搜索、筛选、批量管理；没有证据表明这些是本轮所需。
- charts 模式优先整改；ziwei/meihua/未知 type 的兼容范围须明确记录，不能静默删除现有入口或假装新模块已经接通。

### 4.2 八字详情与 AI 卡片

建议布局保持：

```text
返回入口 / 命盘标识
四柱主盘
AI 解读卡片
  一行公共风格标题 + 唯一折叠开关
  五方面选择（八字专属）
  当前方面说明 / 主动开始按钮
  流式正文 / 重试或重新解读 / 追问
  该方面旧版记录（八字专属）
基本信息、四柱细盘、命局提要、大运流年
```

- 以现有梅花/六爻 AI 卡片为参照，复用卡片边框、圆角、标题、按钮、正文和追问的设计令牌，不复制整套 CSS/逻辑。
- 优先在八字适配器/局部样式内完成；如确需公共引擎支持标题插槽或折叠范围，采用可选配置且默认行为不变，必须三路回归。
- 不保留“自有标题 + 隐藏公共标题”的长期补丁模式，但也不为消掉这段 CSS 大规模重写引擎。统一由一个清晰的所有者负责标题与完整区域的折叠。
- 八字特有样式移到可维护的页面/组件样式文件，避免 JS 注入长 CSS 与主题令牌并存。
- 保留四柱/AI/其余资料顺序；语义数据不因改样式减少；管理员视图仍不挂普通用户 AI 操作。

### 4.3 必须保留的交互契约

- 挂载不自动扣额度，选方面不等于自动发起解读，开始要由用户明确点击。
- 一次显示一个方面；切方面替换而非累积，停止上一方面的流，不能把迟到结果写入另一个方面。
- 折叠只是腾地方，**不中断流、不重发请求**；再展开能看到继续生成的内容。
- 每方面最新一条在前，旧版可展开；不覆写或删除旧记录。
- 游客一次试用、综合需登录、登录回到原方面的既有约束保留。
- 追问围绕当前方面和当前解读；不落为新的历史解读，额度规则不放宽。
- 出错时不能把半截结果标作完整成功；刷新后历史仍可恢复。

## 五、AI 分方面设计（待用户 prompt）

### 5.1 结构建议

在现有后端 prompt 模块中增加显式解析入口；命名是实施建议，不是已存在 API：

```text
buildBaziContext(chart, options)               复用现有上下文生成，不重算盘
resolveBaziPrompt({ aspect, mode, ... })        唯一的方面/首次追问分流入口
  综合 → 用户提供的综合 system + user 模板
  事业 → 用户提供的事业 system + user 模板
  财运 → 用户提供的财运 system + user 模板
  婚姻 → 用户提供的婚姻 system + user 模板
  健康 → 用户提供的健康 system + user 模板
  followUp → 对应方面的追问规则（保留短答与不落库契约）
```

- API 和前端 tab 暂不改名，不新建五条接口。
- 公共盘面与专项输入复用现有 `baziVars` / `baziReportVars` 等，不复制一份算法或 JSON 组织器。
- 对比当前固定八模块要求：专项应由用户模板规定章节，不再默认要求输出全部领域。
- RAG 是证据/上下文，不让检索材料覆盖用户的方面指令；保留当前八字首次检索、追问复用上下文的契约，除非另行批准调整。
- 模板验证需区分公共占位符和专项占位符，未知占位符、缺模板、空内容要在调用模型前被检测。
- 不把缺少模板的专项静默回退成“成功的综合解读”。交付阶段应明确哪些方面仍用旧行为，未就绪部分不宣称完成。
- 不预设要做后台动态编辑。现有八字报告直接使用代码模板；若希望后台可配，应另定版本、权限、回滚及存储范围，避免本轮同时扩大后台与数据库改造。

### 5.2 收到 prompt 后的确认表

每个方面确认：首次 system/user 模板、允许的输入变量、输出章节、篇幅、评分是否保留、流年范围、是否需要补充提问、追问是否另给模板。

若只收到一份方面模板，只验收这一份，不声称五方面全部完成。旧历史不按新 prompt 重写；新旧报告并存是正常情况。

健康内容应避免医疗诊断/治疗指令，其他领域避免保证结果；如用户模板与现有产品安全边界冲突，应先指出差异再接入。
